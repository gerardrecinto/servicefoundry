How a case is built

Each case starts from a vague one-paragraph ask and resolves the ambiguity, which is the real work.

1

Pin the problem

Requirements, scope and what is out of scope, then a domain model with clear ownership of state.

2

Design the contract

API operations with idempotency and error semantics, class responsibilities, and a data model.

3

Argue the trade-offs

Edge cases, rejected options with reasons, a testing strategy and operational notes. Some cases include code that proves the key mechanism.

Run them yourself

cd servicefoundry
scripts/run_examples.sh        # Python solutions
scripts/run_examples.sh --all  # also Java, Go, Ruby, C++
templates/        # section templates every case follows
docs/design-playbook.md
docs/design-rubric.md

Copy the templates into cases/<name>/ to start a new case.

What this does not do
  • These are practice designs and focused reference code, not deployable services.
  • Only four cases have code. The other six are design write-ups.
  • The rate limiter keeps state in one process. The write-up discusses distributed limits, and the code does not implement them.
